01

What Draftlab does

Draftlab is an experiment platform for speculative decoding on software-agent traffic. It connects a real workload, several draft strategies, a custom decoder and a serving stack so that an attractive prediction can be tested against actual generation.

A language model normally generates one token at a time. A token might be part of a word, punctuation or a fragment of code. Each new token depends on the previous ones, so the next model call has to wait. Speculation lets a cheaper drafter propose a short continuation and asks the target model to check the whole continuation in one call.

The motivating workload is this machine’s local Qwen 27B coding agents. Their transcripts include prose, thinking, code and structured tool traffic. Those transcripts supply the data; the experiments in this report use smaller 1.5B and 0.5B targets. They do not measure an acceleration of the original 27B agents.

Model runtime
A Qwen2 implementation in JAX: grouped-query attention, rotary positions, RMS normalization, a gated MLP and a fixed-capacity key/value cache. PyTorch adapters are merged into the JAX weights for decoding.
Serving & visibility
The Go gateway handles API-key authentication, per-key rate limits, model routing and a circuit breaker. It streams responses and exposes Prometheus metrics; Grafana displays latency, tokens, acceptance and backend health.
Experiment tooling
Ray schedules sweep cells. Small JSON/Parquet artifacts feed a React explorer. A separate benchmark compares configurations in one process after compilation warm-up.
Deployment tooling
Dockerfiles, a Helm chart, a host-only kind check and Terraform/GKE configuration exist. They are implementation artifacts; this snapshot does not establish a production deployment or a GPU performance result.
02

A faster path must keep the same distribution

The target stays responsible for the output. A draft token is a proposal; accepting it is a probability calculation.

At a given position, let p be the target’s next-token distribution and q the distribution that actually produced the draft. For sampled decoding, the engine accepts a proposed token x with probability min(1, p(x)/q(x)). On the first rejection it samples a replacement from the normalized positive difference max(0, p − q). If every draft survives, it samples a bonus token from the target.

This accept-and-repair rule preserves the target distribution under its assumptions. Greedy decoding has a simpler rule: keep the proposed token if it equals the target’s top choice. At positive temperature, distribution equality is the goal; two runs need not produce the same text or consume random numbers in the same order. Leviathan et al., 2023; Chen et al., 2023.

The interesting implementation detail: a pending token

The target cache stores every committed token except the newest one. A step feeds [pending_token] + drafts to the target. Logit row j predicts draft j; the final row predicts the bonus token. After accepting A drafts, the engine keeps the pending token and that accepted prefix in its cache. The replacement or bonus becomes the next pending token.

Cache rollback changes the logical length rather than recomputing the prefix. Values beyond that length can remain in the allocated buffers; the attention mask must keep them invisible. The drafter has its own cache and must roll back to the same committed history. This convention removed a second target forward that used to decode the bonus separately. See 1e9f5d3.

Kernel scope. Triton verify and alpha kernels exist with PyTorch references. The alpha evaluator can use the fused alpha kernel on CUDA. The current JAX decoder performs verification in its own loop; the existence of the fused verify kernel does not establish that serving uses it.

03

Data that looks like an agent’s work

The original corpus groups content into thinking, text, fenced code, tool calls and tool results. Blocks are deduplicated and capped at 4,096 tokens. Entire runs belong to a single split, so adjacent blocks from the same session cannot cross the train/evaluation boundary.

The first validation and test splits each had only three runs. An audit also found that one run dominated their token mass. The newer temporal hold-out adds 14,974 blocks, 4.24 million tokens and 14 runs from later traffic, excluding runs already present and exact (kind, text) duplicates from the older splits.

What the headline actually measures

The alpha evaluator scores 700 selected blocks from the temporal hold-out, containing 56,990 token positions. It selects blocks across runs, uses blocks of at most 256 tokens and reconstructs context from preceding selected blocks within a 1,024-token budget. It then scores the recorded prefix at every position—often called teacher forcing.

Alpha is the overlap between the two probability distributions:

α = Σₓ min(p(x), q(x)) = 1 − TV(p, q)

Interpretation

An alpha of 0.71 means about 71% of the distributions’ probability mass overlaps, averaged over this evaluation. With correctly sampled proposals at those contexts, it corresponds to expected acceptance. It is neither 71% next-token accuracy against the corpus nor a promise that 71% of a live draft block will survive.

Uncertainty

The saved estimates are means of 1,000 bootstrap replicates. Each replicate samples whole runs with replacement and pools their token counts. Resampling runs respects session dependence; it does not eliminate uneven run sizes. The intervals describe this sampled workload.

Scope limits. The saved alpha distributions use unscaled softmax, corresponding to temperature 1. The corrected sweep uses 0 and 0.7, a different target and generated continuations. The selected alpha blocks contain no code row, so this edition makes no held-out code-specific alpha claim. No claim of generalization to other agents, models or repositories follows from these data.

04

A learned drafter captures much more overlap

On the held-out workload, LoRA reaches 71.2% overlap against the 1.5B target. N-gram lookup captures roughly a third. The tiny student captures very little.

The DPO adapter’s point estimate is higher by 0.153 percentage points. The intervals overlap substantially. Separate intervals alone cannot decide whether a paired difference is significant; the saved artifacts do not include the run-level paired difference needed to establish that claim. This edition reports a small observed difference, with the effect unresolved.

The pattern is consistent with repetitive tool syntax and task-specific structure helping prediction. This is an interpretation of the observed differences. Establishing that training specifically learned agent structure would also require an unadapted 0.5B baseline and a matched comparison on non-agent text; those comparisons are not established by the current held-out alpha artifacts.

Despite lower KL, the standard student reaches only 1.14% held-out overlap. A compressed training objective can improve while the downstream metric stays poor. The student’s small capacity, limited training and block-only training context are plausible contributors; this experiment does not isolate their effects.

For LoRA, the deployment bridge is concrete: W ← W + (scaling/rank) · B · A. The sweep reads the saved adapter tensors and adds those low-rank updates to the attention and MLP matrices in the JAX model. Training and inference can therefore use different frameworks without a separate PyTorch drafter in the decoding loop.

Open code finding: DPO pair construction needs an audit

The current pair builder chooses d = argmax(q), then applies an acceptance test using the soft q[d] and residual p − q. That does not describe sampling from q. It also prefills a sequence and then feeds its last token again when starting cached generation. These observations come from draftlab/drafters/dpo.py, not a rerun of training. The main decoder’s October 6 fix does not change this separate code path. Rebuild and check pairs before treating the observed DPO difference as evidence for a correct acceptance-aware training method.

06

Overlap is potential. Decoding is the test.

The corrected sweep generates 32 tokens after short held-out prompts, with draft lengths k ∈ {1, 2, 4, 8} and temperatures 0 and 0.7. It uses a Qwen2.5-0.5B-Instruct target. Here the learned drafter and target have similar parameter counts, so this grid is useful for decoder behavior but is a poor basis for a large speedup claim.

Rows are recorded per prompt. A finished prompt is appended to a sidecar file; the driver folds those records into Parquet on completion or restart. The report reads both forms, deduplicates by configuration and prompt index, and leaves the experiment files untouched. Partial work is visible without rerunning a cell.

Generation moves off the recorded corpus as soon as a continuation diverges. An average teacher-forced alpha cannot describe every subsequent context. The sweep also counts every scored draft in its denominator, including draft positions after the first rejection that cannot be committed. A change in k can therefore change the observed accepted/drafted fraction without changing the first-token overlap.

The identity control uses the target itself as the drafter. Its acceptance should be one. With k = 8, the ideal full step emits nine tokens, but a 32-token output cap requires four steps: 32 / 4 = 8 tokens per step. Finite output limits matter when comparing an analytic expectation with a short generation.

The next measurement. tools/bench_speedup.py warms up model shapes, runs configurations in repeated interleaved passes and compares each with target-only decoding on the same prompts. Its result file, results/speedup_bench.json, is absent. A drafter’s acceptance or a timing ratio from shared Ray workers is insufficient evidence of an end-to-end speedup.

07

Quality checks support the algorithm, with limits

The current test suite includes greedy equality, cache parity with a fresh prefill, sampled-distribution checks and a count of target forwards per step. The added positive-temperature tests exercise an identity drafter and the second-token marginal of a mismatched drafter; they check paths that a first-token or greedy-only test can miss.

A separate judge rerun uses held-out prompts on the fixed engine: 0.5B-Instruct target, DPO drafter, k = 4, temperature 0.7, 16 generated tokens. The local qwen-agent judge receives blind comparisons in both presentation orders, with cached responses and a 150-call cap. These are short-output preference checks, not software-task completion tests.

The speculative-versus-target win-rate interval includes 50%. This does not prove equivalence or non-inferiority. Both orders judge the same prompt, so verdicts are correlated; the file’s Wilson intervals treat verdicts as independent and should be read as diagnostic summaries. The order-disagreement count also shows that judging is sensitive to presentation.

Distribution preservation rests on the acceptance rule and implementation checks. A judge can help detect an obvious quality change, but it cannot replace those checks or validate long coding tasks from 16-token continuations.

What “lossless” means in these checks

At temperature zero, generated tokens should equal the target’s greedy continuation. At positive temperature, the distribution should equal target-only sampling within numerical tolerance. A statistical test checks a finite collection of outcomes; it is evidence against a particular defect, not a proof of every possible prompt or state transition. The commit that added the new checks records that they fail on the previous implementation. This report does not claim a fresh rerun of the project’s full test suite.

08

What the fixes taught us

Several of the most useful results came from learning which measurements could be trusted. The following changes are grounded in the repository’s commit history.

SEP 307a84891 ↗

A one-token shift can look like a bad model

Failure. The evaluator scored token i with logit row i, which predicts token i + 1. The resulting low overlap was a measurement error.

Fix. Align logits to next-token labels; mark the first position invalid when no preceding context exists. Known-answer checks compare cross-entropy with Hugging Face’s internally shifted loss and test repeated versus shuffled text.

Lesson: give a metric a case with a known answer before interpreting an unexpected number.

SEP 30ae371e3 ↗

Correct tokens can hide incorrect cache state

Failure. The model drafter decoded the last committed token twice; on full acceptance, its position marker also failed to advance correctly.

Fix. Align proposal positions and rollback. Regression tests compare the drafter’s key/value cache with a fresh prefill and check its next proposal. October 6 subsequently replaced the layout with the pending-token convention.

Lesson: check the state after both rejection and full acceptance, not just the text returned by one step.

OCT 061e9f5d3 ↗

A plausible q is not necessarily the proposal distribution

Failure. Drafts were chosen greedily but reported with soft probabilities, without matching temperature. The accept-and-repair rule then used a distribution that had not produced the token. Positive-temperature output was biased toward greedy choices.

Fix. Sample model drafts from softmax(logits / T) and report that exact distribution; at zero temperature, use a one-hot greedy distribution. The decoder configures the drafter’s temperature and seed. The same change removes the extra target forward.

Lesson: stochastic correctness includes the proposal mechanism, temperature, random keys and state transitions. An identity drafter at positive temperature is a valuable control.

OCT 060158d68 ↗

A transposed bootstrap made uncertainty disappear

Failure. The multinomial call created n_runs replicates with n_boot draws each. Each replicate spread many draws almost evenly across the same few runs, so intervals collapsed around the estimate.

Fix. Create n_boot replicates, each drawing n_runs sessions. A two-run regression fixture with very different acceptance rates requires an interval spanning both.

Lesson: validate the resampling unit and array shape. Small error bars do not establish a small effect when the uncertainty calculation is wrong.

OCT 065f98414 ↗

The workload and comparison need to match the claim

Failure. The initial splits contained too few independent sessions; first-N prompt selection could concentrate a kind in one session. Concurrent sweep wall times were also used for speedup claims.

Fix. Add a later hold-out, pick prompts round-robin across runs, lengthen generation from 16 to 32 tokens, add a 1.5B target option and build an interleaved benchmark with a target-only baseline.

Lesson: acceptance, runtime savings and generalization require different controls. A larger sample of nearly identical context does not supply those controls.

OCT 0648cf15b ↗

Completion semantics belong in the correctness story

Failure. Serving kept generating after end-of-sequence tokens and always returned finish_reason: stop, even at the length limit.

Fix. Stop at the tokenizer’s EOS markers, exclude them from completion text, report stop versus length, and expose a no-drafter model for comparisons.

Lesson: verify the protocol that callers observe, alongside the decoder’s numerical behavior.
