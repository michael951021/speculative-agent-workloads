# Goal: measure how predictable a coding agent is — speculative decoding on this machine's own agent traffic, end to end
> why: done = REPORT.md answers "how many agent tokens could a draft model have guessed, per kind of content, and what speedup does that buy?" with CIs, backed by a working engine, trained drafters, a served gateway with metrics, deploy configs and an interactive explorer.

## Corpus: what agent traffic looks like
> why: the question is about this machine's real agent traffic; the corpus must be clean, labelled by kind and split by run so every later number is trustworthy.
- [x] **Corpus to Parquet** — draftlab/data/corpus.py: data/raw/agent_turns.jsonl → data/corpus/{train,val,test}.parquet (split 80/10/10 by sha1(run)); columns run, project, seq, role, kind, tool, text, n_tokens (Qwen tokenizer). kind: thinking | text | code (fenced blocks split out of text) | tool_use (tool = name) | tool_result; drop blocks < 8 tokens, dedupe exact repeats, truncate at 4096 tokens. data/stats.sql (DuckDB) + `python -m draftlab.data stats` writing results/corpus_stats.json (blocks, tokens per kind/tool/project, length percentiles). Tests: fixture lines → correct kinds, code split, no run in two splits. (id: corpus) (after: models)
  why: the labelled, leak-free corpus every drafter trains on and every metric is broken down by.
- [x] **N-gram lookup baseline** — draftlab/drafters/ngram.py: prompt-lookup drafting (as vLLM's ngram speculator: match the last n∈{1..4} tokens against the block's preceding context + the previous 8 blocks of the same run, propose the next k). Teacher-forced on the val split: greedy acceptance per position and mean accepted length for k∈{1,2,4,8}, per kind; results/ngram.json with bootstrap 95% CIs (resampling runs). Done when the JSON exists and a test checks the matcher on a hand-made sequence. (id: ngram) (after: corpus)
  why: a free, model-less first answer (tool calls and tool results repeat context a lot) and the floor every trained drafter must beat.

## JAX engine
> why: a from-scratch engine shows the mechanics (KV cache, verification, rollback) and gives exact per-step acceptance data that a black-box server would hide.
- [x] **Qwen2 in JAX** — draftlab/jaxlm/model.py: Qwen2 architecture (RMSNorm, RoPE with the config's theta, GQA, SwiGLU, QKV bias, tied embeddings when configured) as pure-function pytrees or Flax NNX; load HF safetensors; preallocated KV cache, jit-compiled prefill and single/multi-token decode steps. Tests: float32 logits match transformers for T0 on 3 prompts (atol 2e-3); 32 greedy tokens identical; tiny_config runs in < 5 s. (id: jaxmodel) (after: models)
  why: the target and drafters must run in one engine that exposes logits and cache control for speculative decoding.
- [x] **Speculative sampling** — draftlab/jaxlm/spec.py: draft k tokens, score k+1 positions with one target call, accept/reject with residual resampling (Leviathan 2023 / Chen 2023), roll back both KV caches; Drafter protocol (propose(ctx, k) → tokens, probs) with ngram and model drafters. Per-step stats (drafted, accepted, per-position accept, wall ms). Tests: T=0 output identical to target greedy; T=1 on tiny_config with vocab 16: chi-square of 20k first tokens vs the target distribution, p > 0.01; rollback leaves cache equal to a fresh prefill. (id: spec) (after: jaxmodel, ngram)
  why: the core algorithm; the distribution test proves it is lossless, which the judge later confirms end to end.
- [x] **Engine server** — draftlab/serve/app.py (FastAPI): OpenAI-compatible POST /v1/chat/completions (chat template from the tokenizer, stream via SSE and non-stream), GET /v1/models; `usage` adds draft_tokens and accepted_tokens; drafter and k chosen per model name (e.g. `qwen0.5b+ngram-k4`). Tests with TestClient on tiny_config: stream chunk order, usage fields, 400 on bad input. (id: engine) (after: spec)
  why: gives the gateway, the judge and the explorer's live demo a real backend with acceptance numbers in every response.

## Drafters
> why: the interesting data is how much a drafter trained on agent traffic beats generic ones; three training methods (distillation, LoRA SFT, DPO) cover the usual toolbox.
- [x] **Alpha metric** — draftlab/eval/alpha.py: teacher-forced along corpus blocks, per position α = Σ min(p, q) and greedy match, for T vs any drafter (HF torch or JAX), batched, top-k-free (full vocab). Aggregate per kind/tool with bootstrap CIs over runs, plus expected tokens per target call and speedup for k∈{1..8} at the measured cost ratio c. Budget flag --blocks (default 400 val blocks, ≤ 256 tokens each). results/alpha/<drafter>.json. Tests: α=1 for identical models, α matches a hand-computed 3-token vocab case. (id: alpha) (after: corpus, models)
  why: one cheap, exact metric that ranks drafters without running full generations, and converts directly into expected speedup.
- [x] **Alpha alignment fixed, known answers** — draftlab/eval/alpha.py slices logits[len(ctx)-1 : len(ctx)+n-1] (row i predicts token i+1; empty ctx → position 0 invalid), default target Qwen2.5-1.5B-Instruct. Known-answer tests on real 0.5B (draftlab/tests/test_alpha_known.py): per-position CE == HF `labels=` loss < 1e-3; val top-1 42.4% (band 40–70%); uniform-q α exact; repeated-block ngram ≈ 1 + shuffled-null collapse. results/alpha/ngram.json re-run (α 0.3341, greedy_corpus 0.3335 pre-fix anchor, tool_use:Edit 0.5632 > text 0.189); NOTES.md "1.2% vs 27B" finding corrected as the bug. (after: -)
  why: every drafter comparison goes through this metric; its current numbers are an off-by-one artifact.
- [x] **Re-run stale tiny.json with fixed metric** — results/alpha/tiny.json (α 0.0142) was computed with the pre-alphafix off-by-one metric; re-run `python -m draftlab.eval.alpha --drafter hf --draft-model ckpt/tiny/export` on the default 400 val blocks, overwrite the file, compare per-kind values against results/alpha/ngram.json and CLAUDE.md known answers. (id: alphafix)
  why: the only remaining off-by-one artifact number in results/; every drafter comparison goes through this metric.
- [x] **Distilled tiny drafter (JAX)** — draftlab/drafters/distill.py: cache T's top-64 logits on train blocks (--tokens default 1M, data/teacher/*.npz); train a 4-layer d=256 Qwen2-shaped student sharing T's embeddings vocab with Optax AdamW + cosine schedule, loss KL(T‖student) on the top-64 (+ renormalised tail mass); orbax checkpoints in ckpt/tiny/; log loss curves to results/distill_curve.json. Done when val KL falls ≥ 30% from step 0 and results/alpha/tiny.json exists. (id: distill) (after: alpha, jaxmodel)
  why: shows JAX training end to end and tests whether a very small drafter trained on agent traffic is enough.
- [x] **LoRA drafter with FSDP** — draftlab/drafters/lora.py (PyTorch, PEFT): LoRA (r=16, attention+MLP) SFT of Qwen2.5-0.5B on train blocks (this is the 27B agent's own output), sequence packing, `--fsdp` path via torchrun (FSDP wrapping, gloo on CPU, NCCL on GPU), `--qlora` path (bitsandbytes 4-bit, GPU only: exits with a clear message on CPU). Test: `torchrun --nproc_per_node 2` on tiny_config for 5 steps, loss decreases, both ranks save identical adapter weights. Default run: --steps 300 on CPU; adapter in ckpt/lora/; results/alpha/lora.json. (id: lora) (after: alpha, alphafix)
  why: covers production fine-tuning (LoRA/QLoRA) and distributed training (FSDP) while testing whether style-matching the agent raises acceptance.
- [x] **Acceptance-aware DPO** — draftlab/drafters/dpo.py: from spec runs of T with the LoRA drafter at T=1 on train prompts, build pairs (context, chosen = token span the target accepted or resampled, rejected = the drafter's rejected span); TRL DPOTrainer (beta 0.1) on the LoRA adapter; --pairs default 2000. Report α before/after per kind with CIs in results/dpo.json. Test: pair builder on a fake spec log. (id: dpo) (after: lora, spec)
  why: preference optimisation where the "preference" is the verifier's own accept/reject signal — an RLHF-style method with a measurable payoff.

## Kernels
> why: verification is the per-step overhead of speculative decoding; a fused kernel shows GPU-kernel skills and makes the alpha eval cheap at full vocab.
- [x] **Triton verify and alpha kernels** — draftlab/kernels/verify.py: (1) fused verify: given target logits [k+1, V], draft logits [k, V], drafted tokens and uniforms → online-softmax both rows, accept test p/q ≥ u, first-reject index, and the normalised residual max(0, p−q) at that row (one launch, V tiled); (2) fused alpha: Σ min(softmax p, softmax q) per row. Torch reference implementations; tests under TRITON_INTERPRET=1 with V=1000, random logits, fp32 tolerance 1e-5; bench.py prints a table vs torch (skips without CUDA). alpha.py uses the kernel when CUDA is present. (id: triton) (after: boot)
  why: the kernel the GPU run uses for α at 150k vocab, and the clearest demonstration of Triton/CUDA work in the project.

## Serving and observability
> why: a drafter is only useful behind a real API; the gateway turns engine and vLLM backends into one authenticated, rate-limited, observable endpoint.
- [x] **Go gateway** — gateway/ (Go module, stdlib net/http + prometheus/client_golang + slog): OpenAI-compatible reverse proxy for /v1/chat/completions and /v1/models; API keys stored as SHA-256 hashes in config.yaml, Bearer auth; per-key token-bucket rate limit (429 + Retry-After); routing by model name to backends (engine, llama-server, vLLM) with health checks, retries on connect errors and a circuit breaker; SSE passthrough with flushing; /metrics: requests by key/model/status, TTFT and total latency histograms, output tokens/s, draft and accepted token counters from `usage`; serves web/dist at /ui. Tests (httptest fake backends): bad key 401, rate limit 429, stream order preserved, breaker opens after 5 failures and half-opens, metrics counted. (id: gateway) (after: boot)
  why: covers Go, enterprise-style API auth and fault tolerance, and produces the live acceptance metrics the dashboards show.
- [x] **Prometheus and Grafana** — deploy/prometheus/{prometheus.yml,rules.yml} (recording rules: acceptance rate = accepted/draft by model; alerts: acceptance < 0.4 for 10m, p95 TTFT > 2s), deploy/grafana/draftlab.json dashboard (TTFT p50/p95, tok/s, acceptance by model, 429s, breaker state). `promtool check config/rules` in make check; a rules unit test file (promtool test rules). (id: obs) (after: gateway)
  why: observability as code: the same dashboard works locally and in the Helm chart.
